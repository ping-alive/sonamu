`@websocket` 데코레이터는 클라이언트와 서버 사이에 양방향 메시지 채널을 만드는 WebSocket API를 정의합니다. SSE 전용인 `@stream`과 달리 클라이언트가 보내는 이벤트(`inEvents`)도 처리할 수 있고, 같은 namespace/room에 묶인 다른 연결로 메시지를 브로드캐스트할 수 있습니다.

## 기본 사용법

```typescript
import { BaseFrameClass, Sonamu, websocket, type WebSocketContext } from "sonamu";
import { z } from "zod";

const ChatOutEvents = z.object({
  newMessage: z.object({
    id: z.number(),
    content: z.string(),
    userId: z.string(),
  }),
  typingUsers: z.array(z.object({ id: z.string(), name: z.string() })),
});

const ChatInEvents = z.object({
  send: z.object({ content: z.string() }),
  typing: z.object({ active: z.boolean() }),
});

class ChatFrameClass extends BaseFrameClass {
  @websocket({
    namespace: "chat",
    heartbeat: 30_000,
    guards: ["user"],
    outEvents: ChatOutEvents,
    inEvents: ChatInEvents,
  })
  async subscribeChat(
    ctx: WebSocketContext<typeof ChatOutEvents.shape, typeof ChatInEvents.shape>,
  ): Promise<void> {
    const user = ctx.user;
    if (!user) throw new Error("unauthenticated");

    await ctx.ws.join("global");
    await ctx.ws.setUserId(user.id);

    ctx.ws.onMessage("send", async (data) => {
      await Sonamu.websocketRuntime.publishToRoom(
        "global",
        "newMessage",
        { id: Date.now(), content: data.content, userId: user.id },
        "chat",
      );
    });

    await ctx.ws.waitForClose();
  }
}
```

<Info>0.12부터 room/user 변경과 runtime publish는 `Promise<void>`를 반환합니다. 다음 단계 전에 presence store 반영을 보장하려면 `await`하세요. 이 promise는 reject하지 않으므로 `await` 없이 호출해도 안전합니다.</Info>

## 옵션

### outEvents

서버 → 클라이언트로 보낼 이벤트의 타입을 Zod 스키마로 정의합니다.

**필수 옵션**

```typescript
import { z } from "zod";

const OutEvents = z.object({
  ready: z.object({ history: z.array(z.string()) }),
  newMessage: z.object({ id: z.number(), content: z.string() }),
});
```

Sonamu는 시작할 때 모든 `@websocket` route의 `outEvents`를 route 경로를 키로 runtime의 route table에 등록합니다. runtime publish는 이벤트를 선언한 route마다 payload를 한 번 검증·인코딩하고, 각 연결은 자기 route의 frame을 받습니다. 같은 namespace의 route들이 같은 이벤트 이름에 서로 다른 스키마를 선언해도 되며, 이벤트를 선언하지 않은 route의 연결은 건너뜁니다.

### inEvents

클라이언트 → 서버로 들어올 이벤트의 타입을 Zod 스키마로 정의합니다.

**필수 옵션**

```typescript
const InEvents = z.object({
  send: z.object({ content: z.string() }),
  setPeriod: z.object({ period: z.enum(["7", "30", "all"]) }),
});
```

<Info>들어온 이벤트는 envelope을 거쳐 `inEvents`로 검증되며, 검증에 실패하면 핸들러에 전달되지 않습니다. 스키마에 없는 이벤트는 `1008 Policy Violation`으로, 검증에 실패한 페이로드는 `1007 Invalid Frame Payload Data`로 연결을 close합니다.</Info>

### path

WebSocket 엔드포인트 경로를 지정합니다.

**기본값:** `/{modelName}/{methodName}` (camelCase)

```typescript
@websocket({
  outEvents,
  inEvents,
  path: "/realtime/chat",
})
async subscribeChat(ctx: WebSocketContext) {}
```

### namespace

같은 서버 안에서 라우팅·브로드캐스트의 범위를 가르는 논리적 그룹입니다. `Sonamu.websocketRuntime.publishToRoom(roomId, event, data, namespace)`로 보낼 때 같은 namespace의 연결에만 전달됩니다.

**기본값:** `"default"`

```typescript
@websocket({ outEvents, inEvents, namespace: "chat" })
```

### heartbeat

연결 유지를 위한 ping 간격(밀리초)입니다.

**기본값:** `30000` (30초)

```typescript
@websocket({ outEvents, inEvents, heartbeat: 15_000 })
```

### guards

접근 권한을 지정합니다.

```typescript
type GuardKey = "query" | "admin" | "user";
```

```typescript
@websocket({ outEvents, inEvents, guards: ["user"] })
```

가드는 WebSocket upgrade 뒤, 핸들러 실행 전에 실행됩니다. `guardHandler`가 `UnauthorizedException` 같은 4xx Sonamu 예외를 던지면 `1008 Policy Violation`으로, 그 밖의 오류면 `1011`로 연결을 close합니다.

### description

WebSocket API 설명을 추가합니다.

```typescript
@websocket({
  outEvents,
  inEvents,
  description: "전역 채팅 채널을 구독합니다.",
})
```

### resourceName

생성되는 서비스 파일의 리소스 이름을 지정합니다.

```typescript
@websocket({ outEvents, inEvents, resourceName: "Chat" })
```

## WebSocketContext

데코레이터가 적용된 메서드는 마지막 인자로 `WebSocketContext<TOut, TIn>`을 받습니다.

```typescript
type WebSocketContext<TOut, TIn> = BaseContext & {
  transport: "ws";
  ws: WebSocketConnection<TOut, TIn>;
};
```

### ctx.ws.publish

해당 연결로만 이벤트를 전송합니다. 동기로 동작하며, `outEvents`에 없는 이벤트이거나 payload 검증에 실패하면 예외를 던집니다.

```typescript
ctx.ws.publish("ready", { history: ["hello", "world"] });
```

### ctx.ws.onMessage

클라이언트가 보낸 이벤트를 처리합니다.

```typescript
ctx.ws.onMessage("send", async (data) => {
  // data는 inEvents.send 스키마로 검증되어 들어옴
});
```

### ctx.ws.onClose

연결이 닫힐 때 정리 작업을 수행합니다. 콜백이 실행되기 전에 연결은 이미 registry에서 제거되고 모든 room과 사용자 바인딩도 해제되므로, 여기서 `leave`를 호출할 필요는 없습니다.

```typescript
ctx.ws.onClose(() => {
  clearTypingState(user.id);
});
```

### ctx.ws.waitForClose

연결이 끝날 때까지 핸들러를 살아있게 유지합니다. WebSocket 메서드는 보통 이 promise를 await하며 마무리됩니다.

```typescript
await ctx.ws.waitForClose();
```

### ctx.ws.join / ctx.ws.leave

브로드캐스트 단위인 room에 연결을 가입/탈퇴시킵니다. 둘 다 `Promise<void>`를 반환합니다.

```typescript
await ctx.ws.join("room-1");
await ctx.ws.leave("room-1");
```

### ctx.ws.setUserId / ctx.ws.clearUserId

연결에 사용자 식별자를 붙여 `publishToUser`의 타겟이 되게 합니다. 둘 다 `Promise<void>`를 반환합니다.

```typescript
await ctx.ws.setUserId(user.id);
await ctx.ws.clearUserId();
```

사용자 ID는 값뿐 아니라 타입까지 같아야 매칭됩니다. `setUserId(1)`로 바인딩한 연결은 `publishToUser("1", ...)`를 받지 않습니다. 바인딩과 발행에 같은 타입을 쓰세요.

### 변경 동작

`join`, `leave`, `setUserId`, `clearUserId`는 호출 시점에 노드 로컬 registry를 동기로 갱신합니다. 그래서 `ctx.ws.join("r")` 직후 발행한 publish는 `await`하지 않았더라도 이 연결에 도달합니다. 반환된 promise는 그 변경에 대한 presence store 호출이 resolve되거나 실패한 뒤 settle되며, 한 연결의 store 호출은 호출 순서대로 실행됩니다.

이 promise는 reject하지 않습니다. presence store가 실패해도 노드 로컬 상태는 갱신된 채로 남고, 그 연결의 이후 변경도 순서대로 실행되며, 실패는 `ws.registry.mutation.failed` telemetry 이벤트로 기록됩니다. 이미 닫힌 연결에 대한 변경은 무시되고 `ws.registry.mutation.skipped`가 기록됩니다.

## 브로드캐스트

핸들러 밖에서도 `Sonamu.websocketRuntime`을 통해 같은 채널의 다른 연결에 메시지를 보낼 수 있습니다.

```typescript
import { Sonamu } from "sonamu";

await Sonamu.websocketRuntime.publishToRoom(
  "global",
  "newMessage",
  { id: 1, content: "hello" },
  "chat", // namespace
);

await Sonamu.websocketRuntime.publishToUser(
  userId,
  "notify",
  { kind: "mention" },
  "chat",
);
```

| 메서드 | 시그니처 |
| --- | --- |
| `broadcast` | `(event, data, namespace?) => Promise<void>` |
| `publishToRoom` | `(roomId, event, data, namespace?) => Promise<void>` |
| `publishToUser` | `(userId, event, data, namespace?) => Promise<void>` |
| `publishToAudience` | `(audience, event, data) => Promise<void>` |

이 메서드들은 reject하지 않습니다.

- 어떤 route도 선언하지 않은 이벤트이거나 payload가 route의 `outEvents` 스키마 검증에 실패하면, 해당 route의 연결에는 아무것도 보내지 않고 연결도 닫지 않으며 `ws.publish.rejected` telemetry를 남깁니다. 스키마가 payload를 허용하는 route는 그대로 받습니다.
- 라우팅이나 cluster bus가 실패해도 로컬 전달은 이뤄지고 원격 전달만 건너뛰며, 실패는 `ws.fanout.*` / `ws.cluster.*` telemetry로 기록됩니다.

한 노드에서 발행한 publish는 로컬이든 원격이든 모든 수신자에게 발행 순서대로 도달합니다.

<Warning>`ctx.ws.publish`는 기존처럼 동기로 동작해, 알 수 없는 이벤트나 잘못된 payload면 예외를 던집니다. 검증 실패를 삼키는 것은 위의 runtime publish 메서드뿐입니다.</Warning>

## presence 조회

조회 API는 `Sonamu.websocketRuntime.registry`에 있습니다.

| 메서드 | 범위 | 반환 |
| --- | --- | --- |
| `getConnection(id)` | 현재 노드 | `WebSocketConnectionMeta \| undefined` |
| `getConnectionCount(namespace?)` | 현재 노드 | `number` |
| `getRoomMembers(roomId, namespace?)` | 현재 노드 | `WebSocketConnectionMeta[]` |
| `getStats()` | 현재 노드 | `WebSocketRegistryStats` |
| `getRoomMemberCount(roomId, namespace?)` | 클러스터 전체 | `Promise<{ count: number; partial: boolean }>` |

노드 로컬 조회는 snapshot 복사본을 반환합니다. 반환된 객체(`rooms` Set 포함)를 바꿔도 registry에는 영향이 없습니다.

`getRoomMemberCount`는 presence store에 모든 노드의 활성 인원수를 물어보며 reject하지 않습니다. store 호출이 throw하거나 reject하면 현재 노드의 인원수를 `partial: true`와 함께 반환하고 `ws.registry.read.failed` telemetry를 남깁니다. runtime은 이 호출에 자체 timeout을 두지 않습니다. Redis 어댑터는 호출이 `commandDeadlineMs`를 넘기면 reject하므로 이 대체 동작으로 이어지지만, 호출이 끝나지 않는 커스텀 store에서는 반환된 promise도 계속 pending 상태로 남습니다.

```typescript
const { count, partial } = await Sonamu.websocketRuntime.registry.getRoomMemberCount("global", "chat");
```

## runtime 설정

`sonamu.config.ts`의 `server.websocket`으로 runtime을 설정합니다. 단일 노드는 기본값으로 충분합니다.

```typescript
export default defineConfig({
  server: {
    websocket: {
      nodeId: "api-1",
      drainTimeoutMs: 5000,
      telemetry: true,
    },
  },
});
```

| 옵션 | 기본값 | 설명 |
| --- | --- | --- |
| `nodeId` | `presenceStore.nodeId`, 없으면 `clusterBus.nodeId`, 없으면 `${hostname()}-${process.pid}-${random}` | 라우팅에 쓰는 노드 식별자. 세션 ID에 포함됩니다. |
| `presenceStore` | `InMemoryWebSocketPresenceStore` | 클러스터 presence replica |
| `clusterBus` | `NoopWebSocketClusterBus` | 노드 간 publish 전송 |
| `telemetry` | 꺼짐 | telemetry 옵션 |
| `drainTimeoutMs` | `5000` | shutdown 시 대기 중인 store 변경과 publish를 기다리는 상한 |

기본 `nodeId`의 랜덤 접미사는 같은 hostname과 PID로 재시작한 컨테이너가 이전 노드의 상태를 물려받지 않게 합니다. `presenceStore`나 `clusterBus`가 runtime의 `nodeId`와 다른 `nodeId`를 가지면 runtime 생성이 실패합니다.

shutdown 시 runtime은 로컬 연결을 닫고, 대기 중인 store 변경과 publish를 최대 `drainTimeoutMs`까지 기다린 뒤 `presenceStore.shutdown()`(정의된 경우)과 `clusterBus.shutdown()`을 호출합니다.

### 커스텀 presence store

모든 메서드는 값이나 promise를 반환할 수 있습니다(`MaybePromise<T> = T | Promise<T>`). 동기 throw는 rejection과 같게 처리됩니다.

```typescript
interface WebSocketPresenceStore {
  readonly nodeId?: string;
  register(input: WebSocketPresenceRegistration): MaybePromise<void>;
  activate(sessionId: string): MaybePromise<void>;
  unregister(sessionId: string): MaybePromise<void>;
  setUserId(sessionId: string, userId: WebSocketUserId): MaybePromise<void>;
  clearUserId(sessionId: string): MaybePromise<void>;
  join(sessionId: string, roomId: WebSocketRoomId): MaybePromise<void>;
  leave(sessionId: string, roomId: WebSocketRoomId): MaybePromise<void>;
  resolveRoute(audience: WebSocketAudience, nodeId: string): MaybePromise<WebSocketRoutingPlan>;
  getRoomMemberCount(roomId: WebSocketRoomId, namespace?: string): MaybePromise<number>;
  shutdown?(): MaybePromise<void>;
}

type WebSocketPresenceRegistration = {
  sessionId: string;
  nodeId: string;
  namespace: string;
  active: boolean;
  connectedAt: Date;
};

type WebSocketRoutingPlan = {
  localSessionIds: string[];
  remoteNodeIds: string[];
};
```

- 각 노드는 자기 세션에 대해서만 store를 호출합니다. 한 세션의 호출은 호출 순서대로, 앞선 호출이 settle된 뒤에 전달됩니다. `unregister`는 항상 `register` 뒤에 옵니다.
- `resolveRoute`는 audience를 호출 노드의 로컬 세션 ID와 중복 없는 원격 노드 ID로 나누며, 비활성 세션은 제외합니다. `connections` audience는 세션 ID에 포함된 노드 ID로 라우팅하므로 store를 호출하지 않습니다.
- `getRoomMemberCount`는 클러스터 전체의 활성 인원수를 셉니다.
- 사용자 ID는 타입까지 같아야 매칭됩니다(`1`과 `"1"`은 다릅니다).
- 조회 메서드는 복사본을 반환해, 호출자가 store 상태를 바꿀 수 없게 하세요.
- 호출 시간의 상한은 store가 직접 두세요. runtime은 throw나 reject를 실패로 처리하지만 timeout은 두지 않으므로, 끝나지 않는 호출이 있으면 그 세션의 이후 변경, 원격 publish 라우팅, `getRoomMemberCount`가 계속 기다립니다. shutdown은 대기 중인 변경과 publish를 `drainTimeoutMs`까지만 기다립니다.

기본값인 `InMemoryWebSocketPresenceStore`는 한 프로세스의 여러 runtime이 한 인스턴스를 공유하면 클러스터 replica로 동작하므로 테스트에 유용합니다.

### 커스텀 cluster bus

```typescript
interface WebSocketClusterBus {
  readonly nodeId?: string;
  publish(envelope: WebSocketClusterEnvelope): void | Promise<void>;
  subscribe(handler: WebSocketClusterEnvelopeHandler): MaybePromise<() => void>;
  shutdown(): void | Promise<void>;
}

type WebSocketClusterEnvelope = {
  id: string;
  sourceNodeId: string;
  targetNodeIds: string[];
  audience: WebSocketAudience;
  event: string;
  frames: Record<string, string>; // route 키 → 인코딩된 frame
  emittedAt: number;
};
```

- 각 envelope은 `targetNodeIds`의 노드에만 전달하세요.
- envelope에는 발행 노드가 이미 검증·인코딩한 frame이 담깁니다. 수신 노드는 자기 메모리로 audience를 해석하고, 각 연결에 그 route의 frame을 재검증 없이 바이트 그대로 보냅니다. 그래서 `z.date()` 필드는 모든 노드에서 같은 ISO 문자열로 도착합니다.
- `subscribe`는 구독 해제 함수를 바로 반환하거나 promise로 반환할 수 있습니다. runtime은 shutdown 시 이 함수를 한 번 호출합니다. `subscribe`가 실패하면 runtime은 로컬 전용으로 계속 동작하고 telemetry로 기록합니다.
- route 키 없이 등록된 연결(예: 직접 만든 runtime의 `registerConnection`으로 등록한 연결)은 로컬 publish만 받습니다.

## Redis 멀티 노드

`@sonamu-kit/websocket-redis-adapter`는 Redis 기반 presence store와 cluster bus를 제공합니다. `sonamu` 0.12.0 이상과 peer dependency인 `redis`(node-redis) `^6`이 필요합니다.

```bash
pnpm add @sonamu-kit/websocket-redis-adapter redis
```

어댑터를 `server.websocket`에 펼쳐 넣으세요. 어댑터의 `nodeId`, `presenceStore`, `clusterBus`가 같은 노드 ID를 공유하므로 runtime의 노드 ID 검사를 통과합니다.

```typescript
import { createRedisWebSocketAdapter } from "@sonamu-kit/websocket-redis-adapter";

export default defineConfig({
  server: {
    websocket: {
      ...createRedisWebSocketAdapter({
        redis: { url: process.env.REDIS_URL },
        prefix: "myapp:ws",
      }),
    },
  },
});
```

`redis` 옵션에는 다음 중 하나를 넘깁니다.

- `RedisClientOptions`: 어댑터가 클라이언트를 만들고 소유합니다.
- 기존 `RedisClient`: 호출자가 소유합니다. 어댑터는 pub/sub용 `duplicate()`만 만들고 닫습니다.
- 기존 `RedisSentinel`: 호출자가 소유합니다. 어댑터는 Sentinel 인스턴스로 구독하므로 failover 뒤에도 pub/sub이 이어집니다.

어댑터는 처음 사용할 때 연결하며, 넘겨받은 클라이언트를 연결하거나 닫지 않습니다. 넘기는 클라이언트나 Sentinel은 직접 `connect()`하고 `error` 리스너도 직접 붙이세요.

| 옵션 | 기본값 | 설명 |
| --- | --- | --- |
| `redis` | (필수) | 클라이언트 옵션, 클라이언트, 또는 Sentinel |
| `nodeId` | `${hostname()}-${process.pid}-${random}` | 노드 식별자. runtime 기본값과 같은 형식입니다. |
| `prefix` | `"sonamu:ws"` | Redis 키와 pub/sub 채널의 접두사 |
| `heartbeatIntervalMs` | `5000` | 노드 생존 정보와 키 TTL을 갱신하는 주기 |
| `nodeTimeoutMs` | `15000` | 이 시간 동안 heartbeat가 없는 노드는 라우팅에서 제외됩니다. |
| `keyTtlMs` | `30000` | 노드 presence 키의 TTL. 비정상 종료된 노드의 키가 만료되게 합니다. |
| `commandDeadlineMs` | `2000` | 어댑터가 Redis 호출마다 적용하는 deadline. 늦은 호출은 `RedisWebSocketDeadlineError`로 reject합니다. 쓰기가 실패하면 노드 presence 재구성을 예약하고, 읽기가 실패하면 reject하므로 runtime이 위에서 설명한 대체 동작을 합니다. |
| `readyTimeoutMs` | `3000` | 첫 연결이 ready가 되기를 기다리는 최대 시간. 그때도 Redis를 쓸 수 없으면 쓰기가 실패하고, 등록은 재구성 전까지 메모리 전용으로 resolve합니다. |
| `drainTimeoutMs` | `5000` | 어댑터 종료 시 대기 중인 작업을 기다리는 최대 시간 |

패키지는 `REDIS_WEBSOCKET_ADAPTER_DEFAULTS`(위 기본값)와 `RedisWebSocketDeadlineError`도 export합니다. `presenceStore.getStatus()`는 `{ ready, rebuildPending }`을 반환합니다.

실패 처리:

- 재구성 대기 상태는 standalone 클라이언트의 `ready`(재연결), Sentinel `MASTER_CHANGE`, 다음에 성공한 heartbeat 중 먼저 오는 시점에 노드 presence 키 전체를 메모리 상태로 다시 써서 해소합니다.
- heartbeat는 노드 presence 키가 남아 있는지도 확인합니다. 메모리상 있어야 할 키가 Redis에서 사라졌으면(eviction, `FLUSHDB` 등) 실패한 명령이 없어도 재구성을 예약합니다.
- `getRoomMemberCount`는 이 노드의 멤버를 메모리에서 세고 다른 노드의 멤버만 Redis에서 읽으므로, 이 노드의 키를 재구성하는 동안에도 수가 정확합니다.
- Sentinel에서는 failover로 최근 쓰기가 유실될 수 있으므로 새 `MASTER_CHANGE`마다 재구성을 예약합니다. 같은 master에 대한 반복 이벤트는 무시하고, 짧은 간격의 이벤트는 debounce해 한 번만 재구성합니다. failover 뒤 `EVALSHA`가 `NOSCRIPT`로 실패하면 `SCRIPT LOAD` 뒤 한 번 재시도합니다.
- cluster bus 구독이 시간 안에 끝나지 않으면 `subscribe`가 reject하고 runtime은 `ws.cluster.subscribe.failed`를 기록합니다. 어댑터는 구독 요청을 유지했다가 연결이 ready가 되면 구독을 마치므로, 이 노드는 다시 원격 publish를 받습니다.

<Warning>여러 애플리케이션이 Redis 하나를 공유하면 애플리케이션마다 다른 `prefix`를 지정하세요. 클라이언트의 `keyPrefix`는 키에만 적용되고 pub/sub 채널에는 적용되지 않으므로, `prefix`가 같은 두 애플리케이션은 서로의 클러스터 메시지를 받게 됩니다.</Warning>

## 0.12 마이그레이션

- **변경 메서드 비동기화**: `ctx.ws.join`, `leave`, `setUserId`, `clearUserId`가 `Promise<void>`를 반환합니다. `await`를 붙이세요. reject하지 않으므로 `await` 없는 기존 호출도 동작하지만, store 반영을 전제로 하는 코드는 `await`해야 합니다.
- **publish 비동기화**: `Sonamu.websocketRuntime.broadcast`, `publishToRoom`, `publishToUser`, `publishToAudience`가 `Promise<void>`를 반환하며 reject하지 않습니다.
- **등록 비동기화**: `WebSocketRuntime#registerConnection`은 `Promise<WebSocketConnection>`을, `activateConnection`은 `Promise<void>`를 반환합니다. runtime을 직접 다루는 코드는 둘 다 `await`해야 합니다.
- **사용자 ID 타입 매칭**: `setUserId(1)`은 더 이상 `publishToUser("1", ...)`와 매칭되지 않습니다. 바인딩과 발행에 같은 타입을 쓰세요.
- **잘못된 runtime publish가 연결을 닫지 않음**: 알 수 없는 이벤트나 검증에 실패한 payload는 해당 route에 대해 버려지고 `ws.publish.rejected` telemetry가 남습니다. 수신자를 `1011`로 닫지 않습니다. `ctx.ws.publish`는 여전히 예외를 던집니다.
- **presence 조회**: `getRoomMembers`는 노드 로컬 snapshot을 반환합니다. 클러스터 전체 인원수는 `await registry.getRoomMemberCount(roomId, namespace)`로 조회하고 `partial`을 확인하세요.
- **기본 `nodeId`**에 랜덤 접미사가 붙습니다(`${hostname()}-${process.pid}-${random}`). 세션 ID에 노드 ID가 포함됩니다.
- **커스텀 store와 bus**: `WebSocketPresenceStore`와 `WebSocketClusterBus`가 바뀌었습니다. store는 `resolveRoute`를 구현하고 promise를 반환할 수 있습니다. envelope은 `data` 대신 route별 인코딩된 `frames`를 담습니다. `subscribe`는 promise를 반환할 수 있습니다.
- **shutdown**은 대기 중인 store 변경과 publish를 최대 `drainTimeoutMs`(기본 `5000`)까지 기다립니다.

## 다른 데코레이터와 함께 사용

`@websocket`은 `@api`, `@stream`, `@upload`와 같은 메서드에 동시에 사용할 수 없습니다. WebSocket으로 구독하면서 동일 데이터를 일반 HTTP로도 조회하고 싶다면, 메서드를 분리해 한쪽은 `@api`로, 다른 한쪽은 `@websocket`으로 노출하세요.

```typescript
class DashboardFrameClass extends BaseFrameClass {
  @api({ httpMethod: "GET" })
  async getRecentActivity(period: ActivityPeriod = "7"): Promise<ActivityGroup[]> {
    // ...
  }

  @websocket({ outEvents, inEvents })
  async getRecentActivityStream(
    initialPeriod: ActivityPeriod = "7",
    ctx: WebSocketContext<typeof outEvents.shape, typeof inEvents.shape>,
  ): Promise<void> {
    // ...
  }
}
```

## 제약사항

### 1. @api / @stream / @upload와 중복 사용 불가

```
@websocket decorator can only be used once on Chat.subscribe.
You can use only one of @api, @stream, @websocket, or @upload decorator on the same method.
```

### 2. httpMethod는 항상 GET

`@websocket`은 자동으로 `httpMethod: "GET"`을 설정합니다. WebSocket upgrade는 GET 요청에서 시작되기 때문입니다.

### 3. createSSE / reply에 의존하는 contextProvider 사용 시 주의

WebSocket 경로에서는 SSE 헬퍼나 FastifyReply 접근이 의미가 없어 접근하면 즉시 에러가 발생합니다. 컨텍스트가 SSE/reply에 의존한다면 `websocketContextProvider`를 별도로 정의하세요.

## 클라이언트 사용 (Web)

`@websocket`이 붙은 메서드에 대해 Sonamu는 `useWebSocketChannel` 훅을 자동 생성합니다.

```typescript
import { ChatService } from "@/services/ChatService";

function ChatRoom() {
  const channel = ChatService.useSubscribeChat(
    {},
    {
      newMessage: (msg) => {
        // outEvents.newMessage 데이터
      },
      typingUsers: (users) => {
        // outEvents.typingUsers 데이터
      },
    },
  );

  return (
    <div>
      <div>{channel.isConnected ? "connected" : "disconnected"}</div>
      <button onClick={() => channel.send("send", { content: "hi" })}>send</button>
    </div>
  );
}
```

`useWebSocketChannel`이 반환하는 상태:

```typescript
type WebSocketChannelState<TSend> = {
  isConnected: boolean;
  error: string | null;
  retryCount: number;
  readyState: number;
  send<K extends keyof TSend>(event: K, data: TSend[K]): void;
  close(code?: number, reason?: string): void;
};
```

옵션:

```typescript
type WebSocketChannelOptions = {
  enabled?: boolean;
  retry?: number;
  retryInterval?: number;
  protocols?: string | string[];
  traceProvider?: () => string | undefined;
};
```

[DEBUG] websocket: ChatFrame.subscribeChat

## @stream과의 차이

| 항목 | `@stream` (SSE) | `@websocket` |
| --- | --- | --- |
| 방향 | 서버 → 클라이언트 (단방향) | 양방향 |
| 클라이언트 이벤트 처리 | 불가 | `inEvents` 스키마로 수신 |
| 브로드캐스트 | SSE 연결마다 수동 발행 | `room` / `userId` 기반 라우팅 지원 |
| HTTP 메서드 | GET (자동) | GET (자동, upgrade) |
| 자동 생성 클라이언트 | `eventSource` 헬퍼 | `useWebSocketChannel` 훅 |
