---
title: "migrate"
description: "Managing database migrations"
---

The `pnpm sonamu migrate` commands manage database schema changes. Sonamu compares your Entity
definitions with a database schema, generates Knex migration files from the difference, and applies
them to the databases you choose.

## Basic Concept

- **Entity-based**: `migrate generate` writes migration code from the difference between Entities
  and the database
- **Files in Git**: generated migrations are stored in `src/migrations/` and committed like any
  other source file
- **Explicit execution**: commands that change a database are dry-runs unless you pass `--execute`
- **Multiple databases**: each Sonamu DB preset (`development`, `staging`, `production`, `test`,
  `fixture`) is a separate migration target

## Commands

| Command                                                 | Description                                                      |
| ------------------------------------------------------- | ---------------------------------------------------------------- |
| `migrate status`                                        | Show each connection's applied version and pending migrations    |
| `migrate generate`                                      | Write migration files for Entity changes into `src/migrations/`  |
| `migrate run [--execute]`                               | Apply pending migrations to the database for the current `NODE_ENV` |
| `migrate apply TARGET... [--execute]`                   | Apply pending migrations to the listed targets                   |
| `migrate preview TARGET [--action apply\|rollback]`     | Show which migration files an apply or rollback would run        |
| `migrate code TARGET`                                   | Show the migration code that would be generated against a target |
| `migrate connections`                                   | List the configured migration connections                        |
| `migrate shadow test\|fixture [--execute]`              | Apply pending migrations to a temporary copy of a database       |
| `migrate rollback TARGET [--execute]`                   | Roll back the latest applied batch on one target                 |

`TARGET` is one of `development`, `staging`, `production`, `fixture`, and `test`.

### status - Check Status

```bash
pnpm sonamu migrate status
```

For every connection, the result lists the current version and pending migration files. It also
lists **prepared migrations**: the code Sonamu would generate for Entity changes that do not have a
migration file yet.

### generate - Generate Migration Files

```bash
pnpm sonamu migrate generate
```

- Takes no name argument. File names are derived from the change, for example
  `20240116103045_create__posts.ts` or `20240116103046_alter_users_add1.ts`.
- Files generated together are timestamped one second apart, so their order is stable.
- Generation compares against a connection that has no pending migrations. If every connection has
  pending migrations, the command fails with `MIGRATION_NOT_READY`; apply them first.

### run - Apply to the Current Environment

```bash
# Development (NODE_ENV unset or development)
pnpm sonamu migrate run --execute

# Production
NODE_ENV=production pnpm sonamu migrate run --execute --force-reason CHANGE_REQUEST
```

- `run` applies pending migrations to the preset for the current `NODE_ENV`. With
  `NODE_ENV=test`, it applies to both `test` and `fixture`.
- Without `--execute`, `run` is a dry-run and changes nothing. Use `migrate preview TARGET` to see the
  plan.
- `run` does not generate migrations. Run `migrate generate` first.
- Under `NODE_ENV=production`, `--force-reason` is required.

### apply - Apply to Explicit Targets

```bash
# Check the plan first
pnpm sonamu migrate preview development --action apply

# Apply to several targets in order
pnpm sonamu migrate apply development test --execute

# Production requires a reason
pnpm sonamu migrate apply production --execute --force-reason CHANGE_REQUEST
```

In a TTY, omitting the targets opens a target selection prompt.

### shadow - Validate on a Temporary Copy

```bash
pnpm sonamu migrate shadow test --execute
```

Sonamu creates `<database>__migration_shadow` from the `test` (or `fixture`) database as a template,
applies the pending migrations there, and drops it afterward. Only `test` and `fixture` are accepted.

### rollback - Roll Back the Latest Batch

```bash
# See which files would be rolled back
pnpm sonamu migrate preview development --action rollback

# Roll back the latest applied batch
pnpm sonamu migrate rollback development --execute
```

The target argument is required; `NODE_ENV` does not supply it. A `production` rollback also
requires `--force-reason`.

<Info>
  Commands that change a database ask for confirmation in a TTY. In non-interactive runs, add
  `--confirm` (for example `--execute --confirm`). See the
  [CLI reference](/en/tools-and-cli/sonamu-cli/reference) for exit codes and JSON output.
</Info>

## Migration Generation

### Change an Entity

Add a property to the Entity, either in Sonamu UI or in the `.entity.json` file:

```json title="src/application/user/user.entity.json"
{
  "id": "User",
  "table": "users",
  "props": [
    { "name": "id", "type": "integer", "desc": "ID" },
    { "name": "email", "type": "string", "length": 255, "desc": "Email" },
    { "name": "phone", "type": "string", "length": 20, "nullable": true, "desc": "Phone" }
  ]
}
```

```bash
# Check prepared migrations
pnpm sonamu migrate status

# Write the migration file
pnpm sonamu migrate generate

# Apply
pnpm sonamu migrate run --execute
```

### Migration Files

Generated migration files are stored in the `src/migrations/` directory.

```typescript title="src/migrations/20240116103045_alter_users_add1.ts"
import type { Knex } from "knex";

export async function up(knex: Knex): Promise<void> {
  await knex.schema.alterTable("users", (table) => {
    table.string("phone", 20).nullable();
  });
}

export async function down(knex: Knex): Promise<void> {
  await knex.schema.alterTable("users", (table) => {
    table.dropColumn("phone");
  });
}
```

**Structure**:

- `up()`: Apply migration (create tables, add columns, etc.)
- `down()`: Rollback migration (revert changes)

## Supported Changes

Changes that Sonamu detects and generates migrations for:

| Change Type          | Description         | Example                         |
| -------------------- | ------------------- | ------------------------------- |
| Table creation       | Add new Entity      | Create the `Post` Entity        |
| Column addition      | Add new property    | Add `phone` field               |
| Column modification  | Change type/length  | `varchar(100)` → `varchar(255)` |
| Column deletion      | Remove property     | Delete `deprecated_field`       |
| Index addition       | Define index        | `indexes` array                 |
| Foreign key addition | Define relationship | `BelongsToOne` relation         |

## Multi-Database Management

### Database Configuration

```typescript title="sonamu.config.ts"
export default defineConfig({
  projectName: process.env.PROJECT_NAME ?? "MyApp",
  database: {
    database: "pg",
    defaultOptions: {
      pool: {
        min: 1,
        max: 10,
      },
    },
  },
  // ...
});
```

**Migration targets**:

- Each DB preset (`development`, `staging`, `production`, `test`, `fixture`) is a target
- `*_readonly` presets are never migration targets
- In local environments (`development`, `test`), every target is available; in `staging` and
  `production`, only the preset for the current `NODE_ENV` is

### Applying to Several Databases

```bash
pnpm sonamu migrate apply development test fixture --execute
```

## Practical Workflow

### 1. Change Entity

Add `profile_image` to the User Entity in Sonamu UI or `user.entity.json`.

### 2. Check Status

```bash
pnpm sonamu migrate status
```

The prepared migrations include the new column.

### 3. Generate and Apply

```bash
pnpm sonamu migrate generate
pnpm sonamu migrate run --execute
```

### 4. Update Code

```typescript title="user.model.ts"
class UserModelClass extends BaseModelClass {
  async updateProfileImage(userId: number, imageUrl: string) {
    await this.getPuri("w")
      .table("users")
      .where("id", userId)
      .update({ profile_image: imageUrl });
  }
}
```

## Advanced Usage (Programmatic)

Use the `Migrator` class when you need migrations inside a script.

### Using Migrator Class

```typescript title="src/scripts/migration-tools.ts"
import { Migrator } from "sonamu";

const migrator = new Migrator();

// Apply pending migrations to specific targets
await migrator.apply(["test"]);

// Roll back the latest batch
await migrator.rollback(["development"]);

// Check one connection's status
const status = await migrator.getConnectionStatus("development");
console.log(status.currentVersion, status.pending);
```

`runAction("apply" | "rollback", targets)` still exists for backward compatibility but is
deprecated; call `apply` or `rollback` directly.

### Rollback Script

```typescript title="src/scripts/rollback-migration.ts"
import { Migrator, Sonamu } from "sonamu";

await Sonamu.runScript(async () => {
  const migrator = new Migrator();

  console.log("Rolling back last migration batch...");
  await migrator.rollback(["development", "test"]);
  console.log("Rollback completed!");
});
```

<Warning>
  **Data loss risk**: Rollback can delete tables or columns, so use **very carefully in
  production**.
</Warning>

## Troubleshooting

### Migration Conflict

**Problem**: Multiple developers generated migrations for overlapping changes.

**Solution**:

```bash
# 1. Get latest code
git pull

# 2. Apply the migrations from the other branch
pnpm sonamu migrate run --execute

# 3. Check what is still missing, then regenerate
pnpm sonamu migrate status
pnpm sonamu migrate generate
```

### Database Connection Failed

**Problem**: DB connection failed

```
Error: connect ECONNREFUSED 127.0.0.1:5432
```

**Solution**:

```bash
# 1. Check PostgreSQL is running
psql -U postgres -c "\l"

# 2. List the connections Sonamu uses
pnpm sonamu migrate connections

# 3. Start the local database (generated projects)
pnpm docker:up
```

### Migration Order Error

**Problem**: Applied in wrong order

```
Error: Foreign key constraint violation
```

**Solution**: referenced tables must be created first. Roll back, adjust the file timestamps so the
referenced table comes first, and apply again.

```bash
pnpm sonamu migrate rollback development --execute
# Rename, e.g. 20240116110230_*.ts → 20240116110231_*.ts
pnpm sonamu migrate apply development --execute
```

## Best Practices

### 1. Apply Frequently

Generate and apply migrations in small units instead of accumulating large changes.

### 2. Test Before Production

```bash
# Validate on a temporary copy, then on the test database
pnpm sonamu migrate shadow test --execute
pnpm sonamu migrate apply test --execute

# Check the production plan before applying
pnpm sonamu migrate preview production --action apply
```

See [Production Approval](/en/database/migrations/production-approval) for approval workflows.

### 3. Backup Required

```bash
# Backup before production migration
pg_dump -U postgres myapp_prod > backup_$(date +%Y%m%d).sql

# Apply migration
pnpm sonamu migrate apply production --execute --force-reason CHANGE_REQUEST
```

### 4. Consider Rollback Possibility

```typescript
// ✅ Rollback possible - down() function properly defined
export async function up(knex: Knex) {
  await knex.schema.alterTable("users", (table) => {
    table.string("phone").nullable();
  });
}

export async function down(knex: Knex) {
  await knex.schema.alterTable("users", (table) => {
    table.dropColumn("phone");
  });
}
```

### 5. Version Control with Git

```bash
# Commit migration files to Git
git add src/migrations/
git commit -m "Add phone field to users table"

# Share with team
git push
```
